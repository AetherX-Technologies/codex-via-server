# Codex via Server v0.2 hardened enrollment design

Date: 2026-08-31

Status: approved for implementation planning

Target release: `v0.2.0`

## 1. Summary

Version 0.2 moves all CLIProxyAPI bearer credentials to the server and replaces
the current client-side credential retrieval with restricted, per-device SSH
forwarding. A new device generates its own key, produces a non-secret enrollment
request, and requires one approval from a trusted administrator.

The release also adds explicit compatibility management for the official Codex
CLI and CLIProxyAPI: a version manifest, a `doctor` command, transactional server
upgrades, post-upgrade canaries, and automatic rollback for server components.

The initial client scope is macOS and Windows. Linux support follows after the
same contract is verified on a Linux client.

## 2. Context and evidence

The v0.1 transport solved large Responses API requests being truncated on a
dual-TUN Mac, but it still retrieves a CLIProxyAPI key into the Codex process.
The generated profile prevents project commands from inheriting that key, yet a
malicious process running as the same desktop user can still inspect process
memory or environment state.

That boundary is acceptable for a trusted personal Mac. It is not an acceptable
default for devices the server owner does not fully trust.

The upstream compatibility boundary is also active rather than theoretical:

- Official Codex profiles are a supported interface, but their loading format
  changed in Codex `0.134.0`.
- CLIProxyAPI issue `#5262` records a generated model catalog from CLIProxyAPI
  `7.2.142` that failed in Codex `0.137.0` and worked after upgrading to
  `0.149.1`.
- CLIProxyAPI issue `#5112` records a Responses field accepted by the public
  Responses shape but rejected by the Codex upstream.
- CLIProxyAPI `7.2.146`, published on 2026-08-30, is the currently deployed and
  latest release at design time.

Therefore compatibility must be tested at the HTTP contract and client-profile
boundaries. A matching version number or successful `/models` request is not
enough.

## 3. Goals

1. Keep the real CLIProxyAPI key on the server at all times.
2. Give every client device an independent, revocable SSH identity.
3. Prevent client identities from opening a shell, running commands, forwarding
   arbitrary destinations, or reaching other server services.
4. Preserve local official Codex behavior and local project access.
5. Support macOS and Windows with the same enrollment document and commands.
6. Make a new-device setup short, deterministic, and understandable.
7. Detect incompatible Codex or CLIProxyAPI upgrades before normal use breaks.
8. Roll back failed server upgrades without destroying the last working state.
9. Keep the current v0.1 path available until the v0.2 path passes real tests.
10. Keep the public repository free of server addresses, keys, tokens, OAuth
    files, and production logs.

## 4. Non-goals

- Building a public enrollment website or zero-touch enrollment service.
- Making an approved but compromised client unable to consume API quota.
- Providing per-device API billing or request accounting in v0.2.
- Replacing Tailscale identity and ACL management.
- Forking or modifying CLIProxyAPI internals.
- Managing the official Codex installation by default.
- Claiming Linux support before client-side verification is complete.

An approved device can use the API while its restricted SSH key remains
authorized. Revocation is the control for a lost or abusive device.

## 5. Alternatives considered

### 5.1 Continue retrieving the API key on every client

Advantages:

- Smallest change from v0.1.
- No additional server proxy.

Rejected because:

- The API key crosses into every client trust domain.
- Malware running as the desktop user can steal the credential.
- Revoking one device requires rotating or replacing a shared API key.

### 5.2 Server-side credential injection with restricted SSH

Advantages:

- The real API key never leaves the server.
- Uses mature OpenSSH controls and a loopback HTTP proxy.
- Each device has a separate key that can be revoked independently.
- Keeps normal Codex traffic on the supported Responses HTTP interface.

Decision: selected for v0.2.

### 5.3 Automated enrollment service with one-time codes and mTLS

Advantages:

- Lowest-touch onboarding.
- Can issue short-lived client certificates.

Rejected for v0.2 because:

- Adds a new authentication service and credential lifecycle.
- Expands the server attack surface.
- Requires more monitoring, recovery, and public security maintenance than the
  current number of devices justifies.

## 6. Target architecture

```text
official Codex on macOS or Windows
  -> http://127.0.0.1:<local-port>/v1
  -> per-device restricted SSH local forward over Tailscale
  -> 127.0.0.1:<gateway-port> on the server
  -> loopback HTTP gateway injects Authorization
  -> 127.0.0.1:<cliproxy-port>
  -> CLIProxyAPI Codex OAuth provider
```

Final server state:

- CLIProxyAPI listens on server loopback only.
- The credential-injecting gateway listens on server loopback only.
- OpenSSH is the only client-reachable service used by the product.
- Tailscale ACLs allow approved devices to reach the server SSH port, not the
  CLIProxyAPI or gateway ports.

## 7. Server components

### 7.1 CLIProxyAPI

CLIProxyAPI remains independently installed and versioned. The v0.2 client
depends only on these paths:

- `GET /v1/models`
- `POST /v1/responses`
- Responses server-sent events for streaming

WebSocket transport remains disabled in the Codex profile until the gateway,
upstream, and integration suite all advertise and verify it.

### 7.2 Loopback credential gateway

The gateway uses a mature streaming reverse proxy, initially Nginx, configured
to:

- Listen on `127.0.0.1:<gateway-port>` only.
- Proxy only `/v1/` to CLIProxyAPI loopback.
- Replace any client `Authorization` header with the server-owned key.
- Disable request and response buffering for large POST bodies and SSE.
- Use HTTP/1.1 upstream connections and long streaming timeouts.
- Reject management paths and unexpected URL prefixes.
- Apply conservative request size, connection, and global rate limits.
- Avoid logging authorization headers and request bodies.

The API key is stored in a root-owned configuration fragment with mode `0600`.
Nginx configuration validation must pass before reload.

### 7.3 Restricted SSH account

The server creates a dedicated `codex-tunnel` account with:

- No password.
- No sudo access.
- A non-interactive shell.
- A root-owned authorized-keys file.
- No PTY, agent forwarding, X11 forwarding, user rc, or gateway ports.
- Local TCP forwarding enabled only to the gateway loopback address and port.
- Connection and session limits appropriate for a small number of devices.

Each authorized key line contains one normalized device identifier in its
comment. The administrator tooling edits exact key records and never performs
substring deletion.

## 8. Device enrollment

### 8.1 Enrollment request

`codex-via-server setup` performs local-only work:

1. Detect the operating system and required tools.
2. Generate a dedicated Ed25519 key if one does not exist.
3. Protect the private key with platform-appropriate file permissions.
4. Create an enrollment request containing only public information.

The portable JSON request contains:

```json
{
  "schema_version": 1,
  "device_id": "normalized-device-name",
  "platform": "macos-or-windows",
  "public_key": "ssh-ed25519 ...",
  "requested_at": "RFC3339 timestamp"
}
```

It never contains a private key, API key, OAuth token, admin identity, or VPN
subscription.

### 8.2 Administrator approval

On a trusted administrator Mac:

```text
codex-via-server-admin approve <enrollment-request>
```

Approval:

1. Validates the request schema and device identifier.
2. Displays the public-key fingerprint and target server.
3. Adds one restricted key record through the existing administrator SSH path.
4. Runs `sshd -t` before reloading SSH.
5. Produces a non-secret connection profile for the new device.

The connection profile contains:

- Schema version.
- Tailscale server address or approved MagicDNS name.
- SSH port and restricted username.
- Server SSH host-key fingerprints.
- Gateway destination and recommended local port.
- Codex profile name.
- Minimum supported client version.

The connection profile can be copied through an ordinary private message. It is
not a credential, but its integrity should still be preserved by copying it
from the trusted approval output.

### 8.3 Import and first verification

The new device imports the connection profile and runs:

```text
codex-via-server doctor
```

The normal launcher is enabled only after all mandatory doctor checks pass.

### 8.4 Revocation

```text
codex-via-server-admin list
codex-via-server-admin revoke <device-id>
```

Revocation removes only the exact approved public key, validates the resulting
SSH configuration, and preserves every other device. Because the API key never
left the server, normal device revocation does not require an upstream key
rotation.

## 9. Client interface

Both platforms expose the same user-facing commands:

```text
codex-via-server setup
codex-via-server enroll <connection-profile>
codex-via-server doctor [--live]
codex-via-server update [--check-only]
codex-via-server uninstall
codex-via-server [official Codex arguments...]
```

The implementation is Bash for macOS and PowerShell for Windows. Both consume
the same versioned JSON schema and generate equivalent Codex profiles.

The generated Codex custom provider has:

- A loopback `base_url`.
- `wire_api = "responses"`.
- `supports_websockets = false`.
- No `env_key` and no `requires_openai_auth`.

The client receives no provider secret. Project commands therefore have no
provider credential to inherit or exfiltrate.

## 10. Doctor contract

`doctor` is read-only. It never edits client or server state.

Mandatory checks:

1. Client version and connection-profile schema.
2. Official Codex executable discovery and semantic version.
3. Codex profile parsing using the installed executable.
4. Tailscale route to the configured server.
5. Private-key presence and permissions.
6. Server SSH host-key fingerprint.
7. Restricted forwarding establishment.
8. Authenticated gateway response from `/v1/models`.
9. Cleanup of the local port, SSH process, and temporary files.

`doctor --live` adds one explicitly confirmed, low-output Responses request. A
successful `/models` check is not treated as proof that inference is compatible.

Every failed check reports the failing layer, observed version, expected
contract, and one remediation. It does not print credentials or full request
bodies.

## 11. Compatibility management

### 11.1 Compatibility manifest

The repository maintains a machine-readable `compatibility.json` containing:

- Manifest schema version.
- Minimum supported Codex CLI version.
- Last tested Codex CLI version.
- Minimum supported CLIProxyAPI version.
- Last tested CLIProxyAPI version.
- Supported connection-profile schema versions.
- Required HTTP paths and streaming transport.
- Feature flags such as WebSocket support.

The initial candidate matrix tests Codex `0.149.1`, `0.150.0`, and the current
stable release. The earliest candidate that passes profile parsing, mock
Responses, and doctor tests becomes the declared minimum; v0.2 does not publish
until that value is established by CI. The initial CLIProxyAPI minimum and
tested version are both `7.2.146`, and the initial connection-profile schema is
`1`.

Published manifest values change only after automated checks and one real
canary pass.

### 11.2 Codex upgrades

The project does not silently upgrade Codex. It detects the installed version
and validates the generated profile against that executable.

The public CI matrix tests:

- The declared minimum Codex version where an installable artifact remains
  available.
- The current stable Codex release.
- The generated profile and mock Responses path on macOS and Windows.

A compatibility failure blocks publishing a new project release.

### 11.3 CLIProxyAPI upgrades

Server upgrades are explicit and transactional:

1. Read the requested release metadata and official checksum.
2. Download to a private temporary directory.
3. Verify the checksum before extraction.
4. Back up the current binary, configuration, and unit metadata.
5. Install the candidate without deleting the backup.
6. Restart and verify process health, listener boundaries, `/models`, SSE, and a
   low-output Responses canary through the credential gateway.
7. Commit the new version as current only after all checks pass.
8. Restore the previous binary and configuration automatically on failure.

An update check may run at most once in 24 hours and only reports availability.
No background task installs a new version without an explicit administrator
command.

### 11.4 Private live canary

The server runs a low-frequency private canary after either Codex or CLIProxyAPI
changes. It uses the same gateway path as clients, requests a fixed minimal
answer, records only status, duration, version, and event completion, and never
logs prompts, keys, or OAuth data.

## 12. Migration from v0.1

Migration is additive until the final cutover:

1. Back up the current CLIProxyAPI binary, configuration, systemd unit, and
   client installation metadata.
2. Install and validate the loopback credential gateway.
3. Install the restricted SSH account and validate `sshd -t` without ending the
   existing administrator session.
4. Enroll the current Mac as the first v0.2 device.
5. Run v0.1 and v0.2 side by side on different local and server ports.
6. Pass `doctor --live`, a real interactive Codex task, a large POST, SSE, sleep
   and wake, Tailscale reconnect, and tunnel cleanup checks.
7. Make v0.2 the default launcher while keeping the v0.1 files as a documented
   rollback for one observation window.
8. Enroll and verify the first Windows device.
9. Change CLIProxyAPI from its Tailscale listener to loopback only.
10. Remove client-side API-key retrieval and the v0.1 rollback files.
11. Revoke any client use of the administrator root key.

No migration step deletes the last working path before its replacement passes
the same real request.

## 13. Failure and rollback behavior

- Gateway configuration: validate before reload; restore the previous file on
  failure.
- SSH configuration: validate before reload; preserve an existing administrator
  session until a new restricted login is tested.
- CLIProxyAPI: restore the previous binary and configuration if any smoke or
  canary check fails.
- Codex incompatibility: refuse the new profile and report the supported version
  range; do not modify the default Codex provider.
- Enrollment failure: remove only the partially added device record.
- Revocation failure: leave the original authorized-keys file in place.
- Client update failure: retain the previously installed launcher and profile.
- Network failure: close the local listener and SSH process; never fall back to
  a public CLIProxyAPI address.

## 14. Test strategy

### Public CI

- Bash syntax and behavior tests on macOS.
- PowerShell tests on Windows.
- Versioned enrollment and connection-profile schema tests.
- Invalid device identifier and malformed-key rejection.
- Wrong host fingerprint rejection.
- Restricted `PermitOpen` destination enforcement using a disposable SSH
  server.
- Mock `/models`, large Responses POST, SSE completion, partial stream, timeout,
  and upstream error tests.
- Tunnel lifecycle, signal cleanup, sleep/reconnect simulation, and argument
  passthrough.
- Generated Codex profile parsing for the minimum and current releases.
- Secret scanners over the working tree, Git history, release artifacts, and
  generated logs.

### Private server verification

- Nginx configuration validation and listener checks.
- SSH daemon configuration validation and restricted-account negative tests.
- Confirmation that CLIProxyAPI and the gateway are loopback-only after cutover.
- Confirmation that clients can reach only the SSH port through Tailscale ACLs.
- Real low-output inference, large request, and SSE completion.
- Binary and configuration rollback drill.
- Per-device approval and exact revocation drill.

## 15. Security invariants

The release cannot ship unless all of these statements are true:

1. The CLIProxyAPI bearer key never appears on a client.
2. A client key cannot obtain a shell or execute a remote command.
3. A client key can forward only to the loopback gateway destination.
4. The gateway and CLIProxyAPI are not reachable directly from client devices
   after cutover.
5. The gateway overwrites, rather than trusts, client authorization headers.
6. Logs exclude authorization headers, OAuth material, request bodies, private
   keys, and connection-profile contents that identify a private server.
7. Revoking one device preserves all other device records.
8. An upgrade cannot delete the last verified server binary or configuration.
9. A failed compatibility check cannot silently fall back to a public endpoint
   or the user's default Codex provider.

Version `0.2.0` is a security architecture migration. The release includes:

- Updated English and Chinese README files.
- `MIGRATION.md` with v0.1-to-v0.2 steps and rollback points.
- Administrator server setup and device lifecycle documentation.
- macOS and Windows quick starts.
- `compatibility.json` and its schema documentation.
- Updated `SECURITY.md`, `CONTRIBUTING.md`, and changelog.
- Signed or checksummed release artifacts for both client platforms.

The v0.1 release remains available for historical reference but is documented
as trusted-client-only after v0.2 becomes stable.

## 17. Acceptance criteria

Implementation is complete only when:

1. A fresh macOS device can install, enroll, pass doctor, and run Codex from the
   public release instructions.
2. A fresh Windows device can do the same using PowerShell and Windows OpenSSH.
3. Neither client receives the real CLIProxyAPI key.
4. The restricted account fails shell, arbitrary command, PTY, agent forwarding,
   X11 forwarding, and non-gateway port-forward attempts.
5. Both clients complete a large Responses request and streamed response.
6. Current Codex and CLIProxyAPI versions pass the compatibility manifest and
   private canary.
7. A deliberately broken CLIProxyAPI candidate rolls back automatically.
8. A device can be approved and revoked without changing another device.
9. Server reboot, client reboot, sleep/wake, Tailscale reconnect, and network
   switching recover without exposing a public API path.
10. Public CI, independent security review, reader documentation test, and
    public secret scanning all pass before release.
